# Commit Messages

Craft outcome-focused commit messages derived strictly from diff inspection.

## Workflow

1. **Inspect diff**: Run `git diff --staged` (or the targeted commit diff when rewriting). Use verification output only for context.
2. **Determine scale**: Choose subject-only for simple edits. Add a body only for non-obvious design choices, breaking changes, security fixes, migrations, or reverts.
3. **Draft subject**: Write `<type>(<scope>): <outcome>` in imperative mood.
4. **Draft body & footers**: Use concise bullets or a short paragraph for essential context. Add applicable footers (`Fixes:`, `Closes #N`, `BREAKING CHANGE:`).

*Completion Criterion*: Message is verified against the staged diff, subject fits imperative Conventional Commit syntax (≤72 chars), body is present if risk or non-obvious context warrants it, and all diff changes are accounted for without line-level diff narration or AI trailers.

## Subject

Use Conventional Commits syntax: `<type>(<scope>): <outcome>`.

- **Types**: `feat` `fix` `refactor` `perf` `docs` `test` `chore` `build` `ci` `style` `revert`.
- **Format**: Imperative mood, English, ≤50 chars preferred (hard cap 72), no trailing period. Must fit sentence test: "If applied, this commit will ___".
- **Focus**: State outcome rather than code edit (`fix(auth): reject empty usernames` instead of `fix: add null check in validate()`).
- **Scope**: Subsystem or module name (never a filename); omit for cross-cutting changes.
- **Override**: Follow explicit repository-required commit syntax when required, preserving remaining rules.

## Body

Include a body only when it materially clarifies why a change was made or what non-obvious behavior results.

- **Structure**: Prefer 2–4 concise bullets for distinct points. Use a short paragraph when connected narrative clarifies cause and resolution.
- **Sizing**: Scale by conceptual complexity and risk, not line count. Body is mandatory for complex bug causes, breaking changes, security fixes, data migrations, and reverts.
- **Focus**: Answer what problem motivated the change, what behavior/contract changed, and key design trade-offs.
- **Exclusions**: Omit routine implementation choices, full issue discussions, scope boundaries, deferred work, and duplicated subject text.

## Honesty & Guardrails

- **Single source of truth**: Describe only work actually present in the diff; omit planned follow-ups or local uncommitted edits.
- **Diff separation**: Write what the diff cannot show; omit file lists, line-level diff narration, or restating the subject.
- **Prohibited tokens**: Omit "This commit does X", first-person pronouns ("I"/"we"), emojis, and AI-attribution trailers (`Co-Authored-By: ...`, `Generated by ...`).

## Footers

- `BREAKING CHANGE:` followed by migration steps.
- `Closes #N` or `Refs #N` for issue tracking.
- `Fixes: <12-char sha> ("offending commit subject")` for regressions (always include subject with SHA).

## Examples

### Subject only

```text
docs: fix installation typo
```

### Ordinary change

```text
feat: add commit message guidance

- Replace vague or exhaustive messages with concise, outcome-focused
  guidance.
- Scale body detail to risk and omit information that does not help the
  reader.
```

### Exceptional bug fix

```text
fix(cache): stop retrying permanent failures

Client errors entered the retry loop because every upstream failure was
classified as transient. Treat 4xx responses as terminal while
retaining retries for timeouts and 5xx responses.

This changes retry behavior for callers that previously relied on
repeated 4xx attempts.

Fixes: 1a2b3c4d5e6f ("cache: retry failed upstream requests")
```
